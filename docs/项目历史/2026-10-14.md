## 第五轮：REA 接入失败根因定位与修复（"信任了但没启动"）

**症状**：用户已在连接器管理页点"信任"，但 REA 未启动。
**证据链**：`~/.workbuddy/logs/2026-10-14/workbuddyMainThread__*.log`
```
[MCP-ControllerState] id=custom-mcp:rea state=error error=MCP initialize timed out for "custom-mcp:rea"
[MCP-Lifecycle]  controller.end action=probe elapsedMs=30412
[MCP-ManagerConnect] end state=starting success=false connectMs=30364
```
⇒ WorkBuddy MCP 初始化超时 = **30s**。信任本身是成功的（`mcp-approvals.json` 出现 `...::rea` 条目）。

**受控实验（4 组，唯一变量法）**
| 条件 | 结果 |
|---|---|
| PATH 无 `npx` | 立即退出 1（`'npx' 不是内部或外部命令`） |
| PATH 含托管 node，cwd = **项目目录** | **FAIL，35s 无响应**（进程存活，stderr 仅一行 npm 警告） |
| PATH 含托管 node，cwd = `C:\Windows` | **OK，4960 ms** |
| 直连 `node.exe` + 绝对入口，cwd = 项目目录，env 仅 System32 | **OK，2234 ms** |

**根因**：`npx` 在 Windows 上要经 `cmd.exe` 拼命令行执行包内 bin，而项目路径
`WorkBuddy\极限竞速8 (2)\极限竞速8\极限竞速8` 含**空格 + 圆括号 + 中文** ⇒ **圆括号被 cmd 当作命令分组语法**
⇒ 子进程起不来、npx 永久等待 ⇒ 撞上 30s 超时。**唯一变量是 cwd**，与启动耗时无关
（同一命令在 `C:\Windows` 下 4.9s 正常）。

**修复（最小侵入）**
1. 依赖装到稳定专用前缀：`npm install --prefix C:\Users\Administrator\.workbuddy\mcp-servers\rea rea-agents@6.5.0`
   （257MB，173 包）。**不用 npx 缓存**（`_npx/<hash>` 会被清）。
2. `~/.workbuddy/mcp.json` 的 `command` 改为 `node.exe` **绝对路径**，`args` 改为包内入口**绝对路径** + `mcp`
   ⇒ 零 PATH / 零 shell / 零网络依赖。原 npx 版备份在 `mcp.json.npx-bak-20261014`。
3. 按其自身内容**原样**派生验收：initialize **2288 ms**、`tools/list` 正常、env 仅 System32 ⇒ PASS。

**遗留动作（需用户执行）**：`mcp.json` 已变更 ⇒ **信任哈希失效，需在连接器管理页重新点"信任"**，然后重启会话。

**通用教训（已写入用户级 MEMORY.md）**：MCP server 注册**绝不要用 `npx`/`cmd.exe` 包装**，尤其 cwd 含
空格+圆括号+中文时；应直连 `node.exe` 绝对路径 + 入口绝对路径。
