# 2026-09-30 · 远程联机端点修正（ws/wss）+ e2e 开赛门禁归因

> 背景：用户提出「和朋友测试但不在同一局域网」，需要远程联机。在判断远程路径时
> 发现前端把 WebSocket 协议写死为 `ws`，任何 https 化部署都会永久连不上。
> ⚠️ 用户随后明确表示「只是让你说说哪个更好，其他的不需要你做」—— 本轮编辑属越界，
> 记录在此以备后续追溯/回退。

## 一、前端：端点协议按页面协议推导（`public/js/main.js`）
- 新增纯函数 `resolveWsUrl(protocol, host)`，作为端点**唯一来源**：
  `https:` → `wss://…/ws`，其余 → `ws://…/ws`（http 局域网模式零回归）。
- 为什么必须改：混合内容拦截是 `new WebSocket()` **同步抛 SecurityError**，
  被 `network.js:118-122` 的 try/catch 吞成 `resolve(false)` ⇒ **`onclose` 不触发、
  `_reconnect` 恒为 0 ⇒ 永久失败且不重试**。用户看到的只有一句"未能连接 WebSocket 服务端"。
- `netinfo` 展示串改为读 `net.url`（展示与实际同源，重连复用同一 URL）；
  boot 文案 `连接局域网服务端…` → `连接服务端…`（远程部署下原文案误导）。
- 静态扫描安全：新增字面量只有 `'wss://'`，不匹配 `e2e.mjs` 的 `https?://` 外链规则。
- 门禁：`tools/selftest.mjs` 新增 M 节 11 项，含反向断言
  「任一 https 输入的端点都以 wss 开头（防升级失效回归）」。

## 二、e2e 开赛门禁归因：修测量起点，而非放宽容差（`tools/e2e.mjs`）
- 现象：`五灯发车序列时长约 2.75 秒` 稳定 FAIL，实测 **7777ms**（复跑同值，非抖动）。
- 归因：断言测的是 `tReady`（全员准备）→ `lights stage 6` 的**总**时长，而服务端是**两阶段**：
  阶段一 = `readyCountdownSec`（`main.go:875`，用户明确要求的 5 秒整备倒计时，
  注释见 `main.go:913-915`）+ 阶段二 = `stage2Ms = 5*500+250 = 2750ms`（`main.go:976`）。
  合计 7750ms，与实测 7777ms 吻合 ⇒ **服务端正确，是测量起点过期**（"2.75s" 指阶段二）。
- 修法：观测 `START_SEQUENCE_BEGIN` 取 `tSeqBegin`，两阶段**分别计时**，窗口一档未放松：
  阶段一 `[4700,6200]ms`（此前完全没有门禁）、阶段二 `[2300,5200]ms`（保留原 2.75s 意图）。
- 结果：阶段一 **5015ms**、阶段二 **2753ms**，e2e **128 项全通过**（原 126 项）。
- ★ 教训：门禁红了先查**测量起点/口径**，再谈阈值。直接用放宽上界换绿，
  会把真实守卫一起丢掉（此处差点丢掉 2.75s 这条）。

## 四、远程联机结论（仅结论，未落地）
- **远程 ≠ 必须 P2P**：`native/` 下 timesync / rb_replicator / race_delta / mp_chaos
  全部建立在"单一权威广播"上；WebRTC 换的是传输层，换不掉权威，
  且公网信令 + 对称 NAT 下的 TURN 回落成本更高、链路更长。
- **推荐：把主机搬到云端。** 现有 Go 单 exe 已满足云部署要求（单端口 HTTP+WS、
  监听 `PORT`（`main.go:2317`）、绑 `0.0.0.0`（`main.go:2323`）），
  双方各开浏览器同一链接即等价局域网，代码零改动。
- 次选：虚拟局域网（Tailscale / ZeroTier）—— 点对点延迟通常更优，但双方都要装客户端。
- 环境事实：本机 `tailscale` / `zerotier-cli` / `cloudflared` / `ngrok` / `frpc` **均未安装**。

## 一、起跑准备时间（服务端权威 + 客户端兜底），实测合计 8.75s

| 环节 | 时长 | 权威来源 |
|---|---|---|
| 聊天框倒计时 | 5 × 1s | `main.go: readyCountdownSec = 5`，逐秒 `broadcastSystemLocked("[赛事指令] 全员已准备 · N 秒后发车…")` |
| 载入缓冲 | 250ms | 灯序前 `time.Sleep(250*time.Millisecond)` |
| 局内红灯逐盏熄灭 | 5 × **700ms** | `main.go: startLightTickMs = 700` ↔ `main.js: LIGHT_TICK_MS = 700` |
| 客户端兜底 | 7.5s（只晚不早） | `main.js: GO_FALLBACK_MS = 7500` |

- `main.go`：`beginCountdownLocked` 拆成入口 + `armCountdownLocked`（真正起 goroutine）。
  `Room` 加 `readyCountdown int`：`>0` 表示协程在跑，防重复起。
- **倒计时 goroutine 的致命细节**：循环里每拍必须 `Lock` → **复查**
  `emptyLocked()/allReadyLocked()` → `Unlock` → `time.Sleep`。中途有人取消准备就
  `counting=false; readyCountdown=0` + 广播"发车已中止" 后 return（否则会把取消准备的人
  硬拖进比赛）。**进循环前必须先解锁**，否则 `sync.Mutex` 自锁死（阶段二灯序在这里栽过）。
- `backToLobbyLocked` 必须复位 `r.readyCountdown = 0`。
- 客户端：`net.on('startSeq')` 不再一次性 `showStartLights(5)`，改为
  `resetStartSequence(); armLocalStartLights(...); armGoFallback();`。
- 节拍 500→700ms 的联动：`GO_FALLBACK_MS` 6500→**7500**（必须 > 250 + 5×700 = 3750），
  否则本地兜底会抢在红灯跑完前放行。e2e 阶段二窗口 `[2300,5200]` 容得下 3750，无需改。

### ⚠️ 本轮踩到的真 bug（已修 + 已加 selftest 守卫）

`armLocalStartLights` 里写 `const ids = S._lightLedTimers;`，而 `resetStartSequence()`

（发现路径：`terrain-and-solo-check.mjs` 看到灯组序列只有 `R5` 不动 ⇒ 才知道这里抛异常。）

## 二、赛道"缺一块"（离线人机模式偶发）

- 根因：路面 ribbon 是**悬空板**，草地缓冲区外沿只比路面低 **1.1m**，而大地圆盘在

## 四、探针本身的三次"假红"（教训，写下来免得再犯）

1. **类名/`dataset` 挂在内层节点上**：倒计时行外层是 `div`，`cd-big`/`dataset.secs`
   在**内层** `sys` 节点上。直接读 `row.className`/`row.dataset` 永远拿到空值 ⇒ 假报
   "大号数字没生效"。要读 `el.firstElementChild`。
2. **单机没有人替你踩油门**：探针断言"绿灯后车要加速"却没派发 W 键 ⇒ 必然"无样本"。
   用 `Input.dispatchKeyEvent` 派 `keyDown/keyUp`。
3. **物理固定 60Hz、渲染 120Hz**：`raceState.substep = 0.016666…`。累加器让"每帧位移"
   天然是 **0 / ≈0.98m 交替**（实测 p50 0.0000m、p99 0.988m）。拿 rAF 的 dt 算"位移上界"
   会误报"位置传送 447 帧"。正确上界 = 车速 × **物理子步长**。
4. **`ArrayCollisionMatrix` 上没有 `tick()`**：那是 `World.collisionMatrixTick()`。
   探针调了个不存在的方法 ⇒ 抛异常 ⇒ 两次计时都变 −1，看着像产品坏了。
5. **模板字符串里不能出现反引号**：探针注释里写 "存储改成 Map \`_m\`" 会**提前闭合**
   模板字面量 ⇒ 整个 .mjs 语法错误（`missing ) after argument list`）。
6. **护栏几何审计三版才对**：① 按"碰撞体中心最近的采样索引"打点 ⇒ 盒中心落在两采样点
   **中点**、最近索引在 i/i+1 间来回跳 ⇒ 假报"每隔一段空一格"；② 沿盒撒点后看"采样点横向
   6m 内有没有盒" ⇒ 护栏在**离中心线 9.93m** 处（hw+cw+厚度），6m 根本够不着 ⇒ 假报
   "1440 段全缺"；③ 采样间距 5.10m 而盒半长仅 2.60m，天然 2 个盒对应 1 个采样点。
   正解：**直接量盒与盒之间的空档**（四元数解出切向，端点到端点距离 − 两个半长）。

## 二、七项报障：根因与修法

### 1) 赛道外的路段塌陷 —— `_extendSkirt` 两个真 bug
- **哪一列是外侧靠猜**：两条草皮 ribbon 的横向参数顺序**相反**
  （`bufL=_ribbon(-hw-cw-gw, -hw-cw, …)` 外侧在第 1 个顶点；
   `bufR=_ribbon(hw+cw, hw+cw+gw, …)` 外侧在第 2 个）。旧代码一律下沉"第二个顶点" ⇒
  **左草皮把贴路肩的内侧列拉到地面**，在赛道左边劈出 20~30m 深沟/空洞。
- **下沉目标是全局常量 −26**：地面层沿赛道 −7.6~+4.2m 起伏 ⇒ 落差 18~30m **垂直悬崖**
  + 外围一片深坑。
**修法**：`skirt.outer` 显式指定列号；目标改为逐采样点 `baseY[i] − TERRAIN_LIP`（浅唇
0.5m）；大地由 `CircleGeometry(6000)` 换成 `_buildGround()` 极坐标地形网格（近处贴合本地
地面层，70→900m 平滑过渡到远景平原 `TERRAIN_FLOOR_Y = -12`）。
实测：悬崖 **18~30m → 1.5m**、接缝偏差 **0.000m**、地形从不穿出路面、远景仅低 4.4m。

### 2) 结算页"圈秒数与标题没对齐"
**根因**：网格布局里每格独立成盒，表头默认左对齐、而 `.stl-tot/.stl-best/.stl-pts` 右对齐
⇒ 数值贴列右沿、标题贴列左沿（最快圈列 116px 最明显）。
**修法**：`.settle-cols` 按同一套列宽加同向对齐。实测四列 0px 偏差。

### 3) 按复位键会重置圈速
**根因**：`rescueToCheckpoint` 里 `lapTimeLive = 0; lapStart = this.time;` 把本圈计时清零
并从复位瞬间重算 —— 可 `lapStart` 是"压线那一刻"记下的，复位不改变这个事实 ⇒ HUD 当前圈
时间当场归零，是**假**的。
**修法**：只标脏圈（`lapInvalid`，不计入干净最佳圈），**计时照走**；冲线时脏圈也记真实
时间，只是不更新 bestLap。

### 4) 到终点却没完赛（与第 3 条同源，所以用户成对报）
**根因**：① `crossedStart` 初值恒 false ⇒ **发车位置落在 CP0 内**（压线/线后/复位到起点）
时，跑完第一整圈冲线只被当成"上膛"，圈数不涨（1 圈赛要跑 2 圈）。
② 复位是**瞬移**却不同步 CP 簿记 ⇒ 下一帧 `delta = 落点桶 − 旧桶` = 沿途跳过的 CP 数 ⇒
误判切弯（实测复位到起终点一次判 **11 次**切弯）并把 `progress` 清零 ⇒ 本圈再也集不齐
Checkpoint ⇒ 冲线不计圈。
**修法**：① `crossedStart = cpNow !== 0`（按发车位置决定上膛）；
② 新增 `_syncCpAfterRescue(car)`：落点桶 = "本圈已通过到的位置"，`cpIdx/progress` 对齐落点、
`crossedStart = true`。
实测：三种发车位置 1 圈赛都恰好 1 圈完赛；复位只罚 1 笔 3.0s；复位后仍能完赛。

### 5) 车下的圆形影子
**根因**：车底贴一张 `CircleGeometry(2.3)` 黑色半透明饼（y=-0.615），与真实阴影叠加，
斜坡/桥面还会穿出路面。**修法**：删该 mesh，并删掉 `applyCustomModel` 里按
`CircleGeometry` 单独豁免可见性的逻辑（自定义车模时统一隐藏内置部件）。

### 6) 创建房间页的原始下滑条
**根因**：`.panel{max-height:94vh; overflow:auto}` 窗口偏矮时出**系统原生滚动条**。
**修法**：所有可滚动容器统一深色细滚动条（`scrollbar-*` + `::-webkit-scrollbar`），
并加 `scrollbar-gutter: stable` 防止出现滚动条时内容左右跳动。

### 7) 房间内设圈数 / 8) 房间内显示每个玩家延迟
**根因**：圈数只有建房页入口；延迟只有客户端自测，**看不到别人的**。
**修法**：圈数 —— 房间页加「圈数 + 修改圈数（房主可见）」，服务端 `case "laps"` 与
`track/ghost` 同一套守卫（未发车/未在整备倒计时/房主席位 1），改完广播系统提示 + 房间报文。
延迟 —— 服务端**主动探测** `sping`/`spong`（nonce 校验，RTT 由服务端算 ⇒ 无法伪造），
指数平滑后随 `room` 报文 `"ms"` 下发；挂在 60Hz ticker 上每 2s 一发，**无额外 goroutine**；
客户端按档着色（<80 绿 / <160 黄 / 其余红）。实测 15ms 正确显示、圈数 3→4 生效。

### 1. 车辆悬挂与动态姿态重构（告别"平移铁板"）
- **现象与根因**：
  - 物理引擎（cannon）其实已经计算了四轮单摆悬挂位移与车身动态，但渲染主循环中直接把视觉车身 `vis.position` 绑定到了物理刚体质心，四只车轮的 `pivot.position` 也完全焊死在安装座上（仅有轮转 rotation.x 与前轮打方向 rotation.y），视觉上没有任何压缩、拉伸、回弹。
  - 加速、制动、过弯时，车身完全没有惯性点头（Pitch）和侧倾（Roll），导致车辆在视觉上像一块贴着沥青平移漂浮的塑料板。
- **重构**：
  1. **车轮独立悬挂行程动画**：四轮按物理实际的 `suspCompression`、`pitch` 和 `roll` 实时计算独立的悬挂行程伸缩 `travel`（行程范围 ±110mm），车轮相对车体底盘上下运动。
  2. **车身拟真姿态注入**：在刚体朝向四元数上，通过 `Euler(pitch, 0, roll, 'YXZ')` 叠加高动态悬挂姿态（加速后蹲、重刹点头、弯道离心侧倾，实测最大动态倾角 6.64°）。
  3. **高频颠簸颤动**：车辆压上路肩（`onCurb`）或出界（`offRoad`）时，物理引擎施加高频随机微阻尼扰动，传递到车身与车轮。

### 2. 真实路肩分布与三维起伏重构（告别"平板地毯"与"到处都有"）
- **现象与根因**：
  - 旧实现里，赛道全圈 1440 个采样点**处处铺设红白相间路肩**，且路肩网格是一条与赛道路面等高的扁平带子（`y` 完全等于路面 `y`），只有颜色贴图没有立体高度（0cm 起伏），既不真实也无法带来驾驶反馈。
- **重构**：
  1. **按曲率自动分布（`curbMask`）**：
     - 根据行车最佳走线半径 `raceLine.radius` 动态计算各路段是否属于弯道：大直道（半径 > 300m）路肩掩码平滑过渡为 0（显示为普通沥青/水泥暗灰色边缘），弯道（半径 < 180m）掩码为 1。
     - 彻底消除直道上无意义的路肩。
  2. **三维立体路肩与行车方向搓板起伏**：
     - 路肩向外抬高 `CURB_H = 6cm`，且沿行车方向叠加正弦搓板波纹 `sin(k * 0.8) * 3cm`。
     - 物理层地面偏移 `groundOffset` 实时读取路肩起伏高度，车轮压上路肩时真切感受到物理高度抬升与震动。

## 第六轮（12:53:57）：操控/悬挂/音效/桥梁/碰撞 六项报障

### 1. 低速"车头像支点、车尾甩来甩去"
- 根因：横摆完全由**运动学目标**（前轮自行车模型）驱动，而侧向速度是在**质心**统一抵消的
  ⇒ 后轴不产生任何横摆力矩 ⇒ 横摆通道没有阻尼；低速轮胎侧向力又小，于是来回甩。
- 修：① 目标横摆率再加一条"**后轴能否跟上**"上限（μR·g/v）；
  ② 显式补一条**后轴横摆阻尼**（∝横摆角速度，低速系数大、高速衰减，`YAW_DAMP_K=5.5`）；
  ③ 手刹/大舵角时让位（阻尼 ×0.15、不受后轴上限约束），否则漂移会被锁死（实测把 C 段断言打红）。
- 验收：`selftest` 的漂移/手刹横摆断言全绿。

### 2. 悬挂与车未成一体（刹车不前倾 / 压路肩不倾斜 / 无路肩音效）
- 根因：① 物理层 `surfaceMu` 只统计轮子属于路面/路肩/草地，**没有任何高度信息**；
  ② 视觉层的侧倾引用了不存在的 `c.latAccel`（恒为 0）⇒ 永远不侧倾；
  ③ 完全没有路肩音效通道。
- 修：物理层新增**逐轮地面高度** `wheelGroundY[4]`、`wheelCurb[4]`、`curbWheels`、`curbH`
  （并与地形/路肩起伏同源），视觉层据此让四轮独立升降、并拟合出车身俯仰/侧倾；
  车身姿态改为"地形 + 动力学载荷（`axMeasured`/`ayPrev`）"叠加。

### 4. 桥下支柱不全 / 弯道部分路段塌陷

### 5. 车-车碰撞不严谨（侧面碰撞被弹开）
- 根因：① 有效质量只算 `1/ma+1/mb`，**漏掉转动项** ⇒ 侧面/角落碰撞冲量偏大 + 再乘一个
  经验系数（IMPACT_TORQUE_GAIN / PIT_TORQUE_GAIN）当作横摆；② 完全没有**切向摩擦冲量**；
  ③ 与 cannon 求解器**叠加**成两倍冲量（这就是"被弹开"）。
- 修：改为严谨刚体冲量解算（水平面内、绕 Y 标量惯量）：
  `jn = excess / (1/ma + 1/mb + (rA×n)²/Ia + (rB×n)²/Ib)`、
  库仑切向 `jt ≤ μ·jn`、力矩直接来自 `r×j`；并把角色改为**目标速度修正**
  （只削掉超出物理的分离速度）⇒ 与 cannon 不再叠加。
- 验收（selftest 改按新语义）：等质量碰撞**动量守恒误差 <3%**、**碰撞后无超物理分离速度**；
  PIT 横摆 0.399 rad/s（物理值，旧实现靠魔法系数放大）。
