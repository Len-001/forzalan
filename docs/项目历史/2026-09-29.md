# 2026-09-29 · 帧率事故（7.5fps → 119fps）+ 秒差量纲 + 起跑/房间锁死

> 用户报障原文：**"进入游戏后非常卡……无法确认起步时起步慢的原因，每次都是看到人机
> 走了几步了才起步；左上角的时间差距会乱跳，刚起步就能跳几百的时间差；创建房间只有
> 自己的时候卡顿现象好一点但还是卡；车辆有时会往前一顶一顶的。"**

实测结论：**五个症状是四颗雷，全部在客户端物理/状态机侧，与网络无关。**

## 二、四颗雷

### ① 宽相 NaiveBroadphase × 2963 静态护栏 = O(n²)（**症状：非常卡**）
`world.broadphase = new NaiveBroadphase()` 与 `registerTrackBodies()` 注册的 2963 个
静态 Box 叠加，每物理子步 ~440 万对检测，其中静态-静态对**虽然**被
`needBroadphaseCollision` 立刻否掉，但**函数调用本身**要跑。实测 131ms/帧。

### ② 换成 GridBroadphase 的姿势不对 ⇒ `world.step` 每步抛异常（**未出厂，但源码里躺着**）
cannon 的 `GridBroadphase` 在**构造函数里**就按 `nx*ny*nz` 分配 `bins`/`binLengths`，
之后再改 `nx/ny/nz` 只改索引算术、**不扩容数组**：

```js
const bp = new CANNON.GridBroadphase();   // bins.length = 10*10*10 = 1000
bp.nx = 50; bp.ny = 3; bp.nz = 50;        // 索引算到 7499
```

⇒ idx ≥ 1000 的刚体让 `binLengths[idx]++` 读到 `undefined` ⇒ 抛
`Cannot set properties of undefined (setting 'NaN')` ⇒ 异常从 `world.step` 冒出，
**整帧**（物理 + 视觉同步 + 相机 + HUD + render）全跳过 ⇒ **绿灯亮着车一动不动**。
真机实测复现 100%（2963 刚体里绝大多数都落在 idx ≥ 1000）。

### ③ `Broadphase.makePairsUnique()` 只保留约一半候选对，且会塞 undefined（**只被 Grid/SAP 调用**）
原实现两个游标相向而行（`i++` / `length--`），在中点相遇就退出：

```js
for (let i = 0; i !== t.keys.length; i++) { const key = t.keys.pop(); pairs1.push(p1[t[key]]); delete t[key]; }
```

- **丢掉约一半候选对**（静默漏碰撞）；
- `t.keys` 是**模块级持久数组**，每轮残留一半键；跨轮 pop 到已 `delete` 的键 ⇒
  `p1[undefined]` ⇒ 把 `undefined` 塞进 `pairs1` ⇒ 窄相读 `bi.material` 抛
  `TypeError` ⇒ 整帧中断（实测还会**退化成死循环**：`i` 越过 `length` 后
  `pop()` 空数组返回 undefined 却让 `i !== 0` 恒真 ⇒ 无限 push ⇒ `RangeError`）。
- `NaiveBroadphase.collisionPairs` **不调用**本函数 —— 所以出厂版一直没炸，
  一换宽相才引爆。**这是"换宽相"必须一起修的另一半。**

### ④ `ArrayCollisionMatrix` 是按刚体数**平方**预分配的稠密数组（**症状：越跑越卡、一顶一顶**）
`World` 用它记录"上一步哪些刚体对在接触"，唯一用途是 `collide` 事件只在**新碰撞**
上派发。但：

```js
setNumObjects(n) { this.matrix.length = n*(n-1)>>1 }          // 2967 刚体 ⇒ 4,397,093
reset()          { for (i=0; i!==this.matrix.length; i++) this.matrix[i]=0 }
```

`collisionMatrixTick()` **每个物理子步**清零两次。真机直接计时：
`cm.reset()` 单次 **46.9 ms**、`collisionMatrixTick()` 单次 **52.4 ms**
（占单步物理 98ms 的 53%）。修好宽相后跑到某一刻（JIT/元素种类状态一变）就会
**从 8.3ms/帧持续掉到 110ms/帧直到终场** —— 正是"起步还凑合、越跑越卡、车一顶一顶"。

**关键事实**：会真正接触的对永远是"车 × (车|护栏)"，只有几十个，4.4M 格里
99.999% 从生到死都是 0 ⇒ 换稀疏 Map（`clear()` 即 O(存活条目)，内存从 ~35MB → 几 KB）。

### ⑤ 秒差列量纲错误（**症状：刚起步跳几百秒**）
离线 HUD 的秒差 = `(score(他) − score(我)) / 参考车速`，**它假设 score 单位是米**；
而 `progressScore` 返回的是 `lap*100000 + cpIdx*1000 − 距下一个 CP 的距离`（序号加权）：

- 两车只要跨在一个 Checkpoint 边界两侧，差值里就凭空多出 **1000**（真实 ≈281m
  被说成 1000m），除以起步阶段 12m/s 的下限参考车速 ⇒ **+83 秒**；跨 2~4 个 CP
  就是"跳几百秒"；0.72/0.28 的 EMA 再把它抹成一串乱跳的数字。
- 同段数据实测反证：DOM 峰值 51.2s vs 旧公式本会显示 **98.6s**（且 CP 序号差 3 时
  陈旧公式的虚假份额 = 3000/参考车速）。

**正解**：进程坐标改成**沿中心线的弧长（米）**——赛道采样（`resampleClosed`）是
**等弧长**的，所以 `弧长 = trackIdx × spacing`、跨圈项用**几何压线次数**
`c.lineCross`，天然单调、单位是米，排序与"米差 ÷ 车速 = 秒差"两个用途同时成立。

⚠️ **跨圈项不能用 `c.lap`**（这是同一症状的**第二半**，第一版修完仍会跳）：
`lap` 要集齐全部 Checkpoint 才 +1，而车辆刚越过起终点线时 `trackIdx` 从 ~N-1 跳到 ~0
⇒ 坐标瞬间"后退整整一圈" = 6755m ÷ 起步 12m/s ≈ **几百秒**，排位也会短暂倒置。
`lineCross` 在 `physics.js` 的 `groundConstraint` 里按索引回绕计数（前向 +1 /
倒车 −1，下限 0），**放在 groundConstraint 而非 `updateProgress`** —— 后者只对
`!remote` 调用，而观战/名次需要每台车都有连续坐标。
实测对照（`tools/hud-gap-probe.mjs`）：修前一版 DOM 峰值 **60.0s vs 应有 16.3s**；
修完 DOM **13.5s vs 应有 13.7s**（吻合），同一行相邻采样最大跳变 **1.3s**。

（服务端那一份 `progressScore` 是 **ordinal 排序积分**，只在"双方还没有公共 CP"的
兜底分支里经 `nominalCpMeters` 折成米；权威秒差走 spline 弧长 + 整圈时长 —— 两套
口径不混用，**服务端没有这个量纲错误**。）

### ⑥ `net.on('room')` 能把**正在进行的比赛**踢回大厅（**症状：绿灯起不来 / 别人先走**）
```js
if (m.started) return;      // 只判这一个字段
S.mode = 'room';            // ⇒ 主循环走 else 分支 ⇒ raceClock=0 ⇒ S.rp.racing=false
```
`started` 是 ticker 到点、广播 START 那一刻才置位的 —— 一条在 START 前后擦边送达的
room 报文（实测在 300 轮里偶发）会让 `sampleLocalInput` 第一道闸永久清零油门：
**绿灯亮着、别人的车在跑、我的车永远动不了**。护栏与触发原因无关，已无条件加固。

### ⑦ 时钟轴诊断每场误报
`s.raceClock < -0.001` 在**正常倒计时**（−2.6s）就成立，于是每次发车都打一条
"[raceClock] 发车时刻与本地时钟不在同一时间轴"并 `_clockAxisWarned=1`
（实测联机单人房间 `offN=0.5ms` 完美同步也照报）。判据改成量级阈值
`CLOCK_AXIS_BREAK_S = 30`：正常倒计时保留真值、真换轴（−1e12）必被抓。

## 三、修法与实测选型

| 位置 | 改动 |
|---|---|
| `physics.js` `makeGridBroadphase(world,track,staticBodies)` | **构造参数**传 nx/ny/nz + 包围盒**按实测场景**切（旧 ±1000m 常量连铃鹿都装不下：实测 x∈[-1013,887]、z∈[-696,758]，越界刚体会挤爆边缘 bin）；格边长 40m → **20m**（见下表 A/B） |
| `physics.js` `installGridBroadphaseGuard` | 原型自愈：`bins.length !== nx*ny*nz` 时按当前几何重分配（杜绝"以后再有人在构造后改 nx"） |
| `physics.js` `installMakePairsUniqueFix` | Set 去重 + **显式丢弃空槽**（宁少一对，不崩整帧） |
| `physics.js` `installSparseCollisionMatrix` | 稀疏 Map 取代 4.4M 稠密数组 |
| `main.js` `progressScore` | 弧长（米）；`cpIdx`/`100000` 结构性消失（缺赛道几何时返回 0 + 一次性告警，不再回落到序号加权） |
| `main.js` `net.on('room')` | 比赛进行中直接 return；权威终局只认 `lobby`/`RACE_RESULTS` |
| `main.js` 时钟段 | `CLOCK_AXIS_BREAK_S = 30` 量级判据 |

**宽相选型 A/B**（`tools/broadphase-ab.mjs`，同一段赛道逐相位实测，宽相**单次**耗时）：

| 方案 | 帧间隔 p50 | 宽相 ms/次 |
|---|---|---|
| NaiveBroadphase（出厂） | 116.6 ms | — |
| Grid 10×10×10（构造器默认） | 16.9 ms | — |
| Grid 40m 格（一阶段） | 8.3 ms | 4.02 |
| **Grid 20m 格（采用）** | **8.3 ms** | **2.30** |
| Grid 15m 格 | 8.3 ms | 1.79（bins 25k，收益递减） |
| Grid 10m 格 | 8.3 ms | 1.79（bins 56k，纯浪费） |
| SAPBroadphase | 16.6 ms | 11.79 |

⇒ 格边长是**双向**权衡：候选对 ∝ 格边长²，但每步清零成本 ∝ bin 数量。取 20m。
